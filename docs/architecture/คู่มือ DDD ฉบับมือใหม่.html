คู่มือ DDD ฉบับมือใหม่

Domain-Driven Design อธิบายแบบไม่ต้องมีพื้นมาก่อน เริ่มจากว่ามันแก้ปัญหาอะไร ไปจนถึงสร้าง use case "ยืมหนังสือ" ทีละไฟล์ในโครงสร้างโปรเจกต์จริง

ตัวอย่าง: ระบบห้องสมุด · TypeScript · Express · PostgreSQL · Jest

บทที่ 1

DDD แก้ปัญหาอะไร

ลองนึกถึงโปรเจกต์ที่โตมาสักปี กฎ "ยืมได้ไม่เกิน 3 เล่ม" อาจอยู่ใน controller ตัวหนึ่ง อยู่ใน service อีกตัว และอยู่ใน SQL อีกที่ วันที่ห้องสมุดขอเปลี่ยนเป็น 5 เล่ม ไม่มีใครแน่ใจว่าต้องแก้กี่ที่

DDD คือวิธีจัดโค้ดให้กฎของธุรกิจอยู่รวมกันในที่ที่หาง่าย แยกขาดจากเรื่องเทคนิคอย่าง database และ HTTP โดยมีหลักใหญ่ 3 ข้อ

  • ใช้ภาษาเดียวกับธุรกิจ ถ้าบรรณารักษ์พูดว่า "ผู้ยืม" และ "ยืม" โค้ดก็ควรมี Borrower และ borrow()
  • แบ่งระบบเป็นเรื่องย่อยๆ แต่ละเรื่องมีโมเดลของตัวเอง ไม่ต้องมีคลาสเดียวที่ทุกคนแก้
  • กฎธุรกิจอยู่ในโมเดล ไม่ใช่กระจายใน service หรือ controller

ก่อนและหลังใช้ DDD

ก่อน: กฎ SQL และ HTTP ปนกันในไฟล์เดียว
app.post('/loans', async (req, res) => {
  const m = await db.query(
    'SELECT * FROM members WHERE member_code=$1',
    [req.body.memberCode]);
  if (m.rows[0].status === 'suspended')
    return res.status(409).json(...);
  const c = await db.query(
    'SELECT count(*) FROM loans WHERE ...');
  if (c.rows[0].count >= 3)
    return res.status(409).json(...);
  // อีก 40 บรรทัด...
});

จะเทสต์กฎ "ห้ามยืมเกิน 3 เล่ม" ต้องเปิด DB และยิง HTTP ทุกครั้ง

หลัง: กฎอยู่ในโมเดลที่อ่านเหมือนภาษาคน
class Borrower {
  borrow(copyId, now) {
    if (this.suspended)
      throw new DomainError('MEMBER_SUSPENDED');
    if (this.activeLoans.length >= 3)
      throw new DomainError('LOAN_LIMIT_REACHED');
    return Loan.start(this.id, copyId, now);
  }
}

เทสต์ได้ทันทีโดยไม่ต้องมี DB เปลี่ยนเป็น 5 เล่มแก้ที่เดียว

บทที่ 2

คำศัพท์ 8 คำที่ต้องรู้

DDD มีศัพท์เยอะ แต่ใช้จริงในงานประจำวันแค่ 8 คำนี้ อ่านคำเปรียบเทียบก่อน แล้วค่อยดูตัวอย่างจากห้องสมุด

Ubiquitous Language

ภาษากลางของทีม
เหมือนทีมฟุตบอลที่ตกลงกันว่า "ปิดหลัง" แปลว่าอะไร ทุกคนพูดแล้วเข้าใจตรงกัน

คำศัพท์ที่ทั้งคนทำธุรกิจและ dev ใช้ตรงกัน และใช้ชื่อเดียวกันในโค้ด เช่น ห้องสมุดพูดว่า "ยืม" "คืน" "เกินกำหนด" โค้ดก็มี borrow() return() isOverdue() ไม่ใช่ createLoanRecord() หรือ updateFlag()

Bounded Context

ขอบเขตของเรื่อง
เหมือนแผนกในบริษัท คำว่า "ลูกค้า" ในฝ่ายขายกับฝ่ายบัญชีสนใจข้อมูลคนละอย่าง

ส่วนของระบบที่มีโมเดลและภาษาของตัวเอง ห้องสมุดมี Catalog (หนังสือ), Circulation (ยืมคืน), Membership (สมาชิก) คนคนเดียวกันเป็น Member ใน Membership แต่เป็น Borrower ใน Circulation

Entity

สิ่งที่มีตัวตน
เหมือนคนที่มีเลขบัตรประชาชน เปลี่ยนชื่อ เปลี่ยนที่อยู่ ก็ยังเป็นคนเดิม

วัตถุที่แยกแยะด้วย id ไม่ใช่ด้วยค่าข้างใน การยืมแต่ละครั้ง (Loan) เป็น entity เพราะแม้สองครั้งจะยืมเล่มเดียวกันวันเดียวกัน ก็ยังเป็นการยืมคนละครั้ง

Value Object

ค่าที่ไม่มีตัวตน
เหมือนแบงก์ร้อย ใบไหนก็มีค่าเท่ากัน ไม่มีใครสนใจว่าเป็นใบไหน

วัตถุที่แยกแยะด้วย ค่า และสร้างแล้วห้ามแก้ (immutable) เช่น DueDate (วันกำหนดคืน) Money (ค่าปรับ) ข้อดีคือใส่กฎไว้ในตัวได้ เช่น DueDate.from(now) คำนวณ 14 วันให้เอง ไม่ต้องมีใครบวกวันเองทั่วโค้ด

Aggregate

กลุ่มวัตถุที่ต้องถูกต้องไปด้วยกัน
เหมือนตะกร้าสินค้าที่มีพนักงานเฝ้า จะหยิบเข้าออกต้องผ่านพนักงานคนนั้นเสมอ เขาจะคอยดูว่าไม่เกินโควตา

กลุ่ม entity และ value object ที่มีกฎร่วมกัน มีตัวหลักเรียกว่า Aggregate Root เป็นทางเข้าทางเดียว Borrower เป็น root ที่ถือรายการ Loan ที่ยังไม่คืน กฎ "ไม่เกิน 3 เล่ม" ต้องดูทุก loan พร้อมกัน จึงอยู่ใน Borrower และทุกการยืมต้องผ่าน borrower.borrow()

Repository

ที่เก็บ aggregate
เหมือนห้องเก็บของ บอกว่าขอตะกร้าของคุณสมชาย ก็ได้ตะกร้าทั้งใบมา ไม่ต้องรู้ว่าวางไว้ชั้นไหน

ตัวกลางสำหรับโหลดและบันทึก aggregate ทั้งก้อน domain ประกาศแค่ interface (ต้องการอะไร) ส่วน infrastructure เขียนตัวจริงด้วย SQL หนึ่ง aggregate มีหนึ่ง repository

Domain Service

กฎที่ไม่เป็นของใคร
เหมือนกรรมการตัดสิน ไม่ได้เป็นของทีมไหน แต่ต้องดูทั้งสองทีม

กฎธุรกิจที่ต้องใช้หลาย aggregate และไม่เหมาะจะอยู่ในตัวใดตัวหนึ่ง เช่น FineCalculator ที่คิดค่าปรับจากประเภทหนังสือและประเภทสมาชิก ใช้เมื่อจำเป็นเท่านั้น ถ้ากฎอยู่ใน entity ได้ ให้อยู่ใน entity

Application Service / Use Case

ผู้ประสานงาน
เหมือนพนักงานเคาน์เตอร์ รับเรื่อง หยิบแฟ้ม ส่งให้คนตัดสิน แล้วเก็บแฟ้มคืน แต่ไม่ตัดสินเอง

หนึ่งคลาสต่อหนึ่ง use case เช่น BorrowBook ทำหน้าที่โหลด aggregate จาก repository เรียกเมธอดของ domain แล้วบันทึก ไม่มีกฎธุรกิจ ถ้าเห็น if เรื่องกฎใน use case แปลว่ามันควรย้ายไป domain

ยังมีคำอื่นอีก เช่น Domain Event, Factory, Specification ยังไม่ต้องใช้ตอนเริ่ม พอทีมคล่อง 8 คำนี้แล้วค่อยศึกษาเพิ่ม
บทที่ 3

แบ่ง Bounded Context

นี่คือการตัดสินใจที่สำคัญที่สุด ทำก่อนสร้างโฟลเดอร์ใดๆ วิธีหาง่ายๆ คือถาม 3 คำถาม

  • ใครเป็นคนดูแลเรื่องนี้ คนละกลุ่มคนมักเป็นคนละ context
  • คำเดียวกันมีความหมายต่างกันไหม ถ้าใช่ แยก context
  • เปลี่ยนเรื่องนี้แล้วกระทบเรื่องนั้นไหม ถ้าไม่ค่อยกระทบ แยกได้
Contextดูแลเรื่องคำศัพท์ความซับซ้อน
Catalogหนังสือ ตัวเล่ม บาร์โค้ด ค้นหาBook, Copy, ISBNต่ำ ส่วนใหญ่เพิ่มแก้ค้น
Circulationยืม คืน ค่าปรับBorrower, Loan, DueDate, Fineสูง กฎเยอะ
Membershipสมัคร ต่ออายุ ระงับสมาชิกMember, Statusปานกลาง

คนเดียวกัน สองโมเดล

// membership/domain/member.ts — สนใจข้อมูลส่วนตัวและสถานะ
class Member { id; memberCode; name; email; address; status; suspend(reason) {...} }

// circulation/domain/borrower.ts — สนใจแค่เรื่องการยืม
class Borrower { id; suspended; activeLoans; borrow(copyId, now) {...} }

ถ้ารวมเป็นคลาสเดียว ทีมที่แก้ระบบสมัครสมาชิกอาจทำกฎการยืมพังโดยไม่รู้ตัว แยกกันแล้วแต่ละฝั่งเปลี่ยนได้อิสระ

เริ่มที่ 2–3 context พอ แยกเพิ่มทีหลังง่ายกว่ารวมกลับ ทุก context ใช้ database ตัวเดียวกันได้ แค่ตกลงว่าตารางไหนเป็นของ context ไหน

Value Object: DueDate

domain
src/modules/circulation/domain/due-date.ts
export class DueDate {
  static readonly LOAN_DAYS = 14;

  private constructor(readonly value: Date) {}   // สร้างตรงๆ ไม่ได้ ต้องผ่าน from()

  static from(borrowedAt: Date): DueDate {
    const d = new Date(borrowedAt);
    d.setDate(d.getDate() + DueDate.LOAN_DAYS);
    return new DueDate(d);
  }

  static restore(value: Date): DueDate {         // ใช้ตอนโหลดจาก DB
    return new DueDate(value);
  }

  isPassed(now: Date): boolean {
    return now.getTime() > this.value.getTime();
  }
}

สังเกตว่าไม่มี setter เลย กฎ "14 วัน" อยู่ที่นี่ที่เดียว ใครอยากได้วันกำหนดคืนต้องเรียก DueDate.from()

ไฟล์ 3

Entity: Loan

domain
src/modules/circulation/domain/loan.ts
import { DomainError } from '../../../shared/domain-error';
import { DueDate } from './due-date';

export class Loan {
  private constructor(
    readonly id: number | null,          // null = ยังไม่ได้บันทึก
    readonly borrowerId: number,
    readonly copyId: number,
    readonly borrowedAt: Date,
    readonly dueDate: DueDate,
    private returnedAt: Date | null,
  ) {}

  // การยืมใหม่
  static start(borrowerId: number, copyId: number, now: Date): Loan {
    return new Loan(null, borrowerId, copyId, now, DueDate.from(now), null);
  }

  // โหลดของเดิมจาก DB
  static restore(p: { id: number; borrowerId: number; copyId: number;
                      borrowedAt: Date; dueAt: Date; returnedAt: Date | null }): Loan {
    return new Loan(p.id, p.borrowerId, p.copyId, p.borrowedAt,
                    DueDate.restore(p.dueAt), p.returnedAt);
  }

  isOverdue(now: Date): boolean {
    return this.returnedAt === null && this.dueDate.isPassed(now);
  }

  markReturned(now: Date): void {
    if (this.returnedAt) throw new DomainError('ALREADY_RETURNED');
    this.returnedAt = now;
  }
}

มีสองทางสร้าง: start() สำหรับการยืมใหม่ (มีกฎ) และ restore() สำหรับโหลดจาก DB (เชื่อข้อมูลที่บันทึกไว้แล้ว)

  constructor(
    readonly id: number,
    private readonly suspended: boolean,
    private readonly activeLoans: Loan[],
  ) {}

  borrow(copyId: number, now: Date): Loan {
    if (this.suspended)
      throw new DomainError('MEMBER_SUSPENDED');            // AC5
    if (this.activeLoans.some(l => l.isOverdue(now)))
      throw new DomainError('HAS_OVERDUE_LOANS');           // AC4
    if (this.activeLoans.length >= Borrower.MAX_ACTIVE_LOANS)
      throw new DomainError('LOAN_LIMIT_REACHED');          // AC3

    const loan = Loan.start(this.id, copyId, now);          // AC1
    this.activeLoans.push(loan);
    return loan;
  }
}

นี่คือหัวใจของระบบ กฎการยืมทั้งหมดอยู่ใน 10 บรรทัดนี้ อ่านแล้วเข้าใจได้แม้คนไม่เขียนโค้ด เอาไปให้บรรณารักษ์ช่วยตรวจได้เลย

// borrow-book.ts — UC-01
export class BorrowBook {
  constructor(
    private readonly borrowers: BorrowerRepository,
    private readonly catalog: CatalogLookup,
    private readonly clock: Clock,
  ) {}

  async execute(memberCode: string, barcode: string) {
    const borrower = await this.borrowers.findByMemberCode(memberCode);
    if (!borrower) throw new DomainError('MEMBER_NOT_FOUND');     // AC6

    const copy = await this.catalog.findCopyByBarcode(barcode);
    if (!copy) throw new DomainError('COPY_NOT_FOUND');           // AC6

    const loan = borrower.borrow(copy.id, this.clock.now());      // กฎอยู่ใน domain
    const saved = await this.borrowers.saveNewLoan(loan);
    return { loan: saved, copy };
  }
}

import { Pool } from 'pg';

export class PgBorrowerRepository implements BorrowerRepository {
  constructor(private readonly db: Pool) {}

  async findByMemberCode(code: string): Promise<Borrower | null> {
    const m = await this.db.query(
      'SELECT id, status FROM members WHERE member_code = $1', [code]);
    if (m.rowCount === 0) return null;

    const rows = await this.db.query(
      `SELECT id, member_id, copy_id, borrowed_at, due_at, returned_at
         FROM loans WHERE member_id = $1 AND returned_at IS NULL`, [m.rows[0].id]);

    const loans = rows.rows.map(r => Loan.restore({
      id: r.id, borrowerId: r.member_id, copyId: r.copy_id,
      borrowedAt: r.borrowed_at, dueAt: r.due_at, returnedAt: r.returned_at,
    }));
    return new Borrower(m.rows[0].id, m.rows[0].status === 'suspended', loans);
  }

  async saveNewLoan(loan: Loan): Promise<Loan> {
    try {
      const r = await this.db.query(
        `INSERT INTO loans (member_id, copy_id, borrowed_at, due_at)
         VALUES ($1, $2, $3, $4) RETURNING id`,
        [loan.borrowerId, loan.copyId, loan.borrowedAt, loan.dueDate.value]);
      return Loan.restore({ id: r.rows[0].id, borrowerId: loan.borrowerId,
        copyId: loan.copyId, borrowedAt: loan.borrowedAt,
        dueAt: loan.dueDate.value, returnedAt: null });
    } catch (e: any) {
      if (e.code === '23505') throw new DomainError('COPY_NOT_AVAILABLE');  // AC2: unique index
      throw e;
    }
  }
}

const STATUS: Record<string, number> = {
  MEMBER_NOT_FOUND: 404, COPY_NOT_FOUND: 404,
  COPY_NOT_AVAILABLE: 409, LOAN_LIMIT_REACHED: 409,
  HAS_OVERDUE_LOANS: 409, MEMBER_SUSPENDED: 409,
};

export function httpErrorHandler(err, req, res, next) {
  if (err instanceof DomainError) {
    return res.status(STATUS[err.code] ?? 400).json({ code: err.code, message: err.message });
  }
  console.error(err);
  res.status(500).json({ code: 'INTERNAL_ERROR' });
}

บทที่ 11

ข้อผิดพลาดที่พบบ่อย

Entity มีแต่ getter/setter กฎไปอยู่ใน service

เรียกว่า Anemic Model เช่น loan.setReturnedAt(now) แล้วไปเช็กใน service ว่าคืนไปแล้วหรือยัง แก้โดยให้ entity มีเมธอดที่มีความหมาย loan.markReturned(now) และเช็กกฎข้างในเอง

domain import ของชั้นนอก

เช่น import { Pool } from 'pg' ในไฟล์ domain ทำให้เทสต์ต้องมี DB และผิดกฎทิศทาง ให้ประกาศ interface ใน domain แล้วให้ infrastructure implement

Aggregate ใหญ่เกินไป

เช่นทำ Library ที่ถือหนังสือ สมาชิก และการยืมทั้งหมด โหลดทีหนึ่งช้ามาก และคนแก้ชนกันตลอด aggregate ควรเล็กที่สุดที่ยังรักษากฎได้ Borrower ถือแค่ loan ที่ยังไม่คืนของคนคนเดียว

ส่งแถวจาก DB ออกไปเป็น JSON ตรงๆ

ทำให้ API ผูกกับโครงตาราง แก้ schema ทีไร API เปลี่ยนตาม ให้ผ่าน domain และ mapper เสมอ API ตอบตาม openapi.yaml ไม่ใช่ตามตาราง

shared/ บวมจนเป็นที่ทิ้งของ

ถ้ามีกฎธุรกิจอยู่ใน shared แปลว่ามันเป็นของ context ใด context หนึ่ง ย้ายกลับไป shared ควรมีแค่ของเทคนิคล้วนๆ

แบ่ง context ละเอียดเกินตั้งแต่วันแรก

แยก 10 context ทั้งที่ระบบยังเล็ก ทำให้ต้องเขียนโค้ดเชื่อมเยอะโดยไม่จำเป็น เริ่ม 2–3 ตัว แล้วแยกเมื่อเห็นว่าเรื่องไหนโตจนควรแยก

ตั้งชื่อตามเทคนิคแทนภาษาธุรกิจ

LoanManager, processData(), handleRecord() ไม่บอกอะไร ให้ใช้คำที่บรรณารักษ์ใช้ ถ้าไม่แน่ใจ ถามคนทำธุรกิจว่าเขาเรียกสิ่งนี้ว่าอะไร

บทที่ 12

เมื่อไหร่ไม่ต้องใช้ DDD เต็มรูป

DDD มีต้นทุน คือไฟล์และชั้นเพิ่มขึ้น คุ้มเมื่อกฎธุรกิจซับซ้อน ไม่คุ้มเมื่องานเป็นแค่บันทึกและแสดงข้อมูล

ลักษณะงานแนะนำตัวอย่างในห้องสมุด
กฎเยอะ มีเงื่อนไขซ้อนกัน เปลี่ยนบ่อยDDD เต็ม 4 ชั้นCirculation (ยืม คืน ค่าปรับ)
มีกฎบ้าง ไม่มากมี domain บางๆ หรือรวม application กับ domainMembership (ระงับ ต่ออายุ)
เพิ่ม แก้ ลบ ค้นหาเป็นหลักroute → repository ตรงๆ ใน module ของตัวเองCatalog (ข้อมูลหนังสือ)

แม้ context ที่เรียบง่าย ก็ยังควรอยู่ในโฟลเดอร์ของตัวเองใต้ modules/ และคุยกับคนอื่นผ่าน index.ts เหมือนเดิม วันหนึ่งที่กฎเพิ่มขึ้นค่อยเติมชั้น domain ได้โดยไม่กระทบ context อื่น

บทที่ 13

สรุปหน้าเดียว

ลำดับการทำ use case ใหม่

  • ตัดสินว่า use case นี้อยู่ context ไหน
  • เขียนเทสต์ domain ตาม AC เรื่องกฎ แล้วสร้าง entity / value object / aggregate ให้ผ่าน
  • ประกาศ repository interface ใน domain และ port ใน application ถ้าต้องใช้ข้อมูลจาก context อื่น
  • เขียนเทสต์ use case ด้วย fake แล้วสร้างคลาส use case ใน application
  • เขียน repository จริงใน infrastructure พร้อมเทสต์กับ DB จริง
  • เขียน route และ mapper ให้ตรง openapi.yaml และเพิ่ม error code ใน http-errors.ts
  • ต่อสายใน module.ts และเพิ่ม e2e test

กฎ 5 ข้อที่ต้องจำ

  1. domain ไม่ import อะไรจากชั้นอื่น
  2. กฎธุรกิจอยู่ใน domain เท่านั้น use case แค่ประสานงาน
  3. context อื่นใช้ได้เฉพาะสิ่งที่ index.ts export
  4. เปลี่ยนข้อมูลผ่าน aggregate root เสมอ (borrower.borrow() ไม่ใช่ new Loan() เอง)
  5. ชื่อในโค้ดตรงกับคำที่ธุรกิจใช้
