# UC-03: ผู้ปกครองเติมเงินเข้า Wallet นักเรียน

> สถานะ: ร่างเพื่อรีวิว AC ก่อนออกแบบ Database/API
> Bounded context: `student-account` (ระดับ `full`)
> แหล่งที่มา: [PRD](../../product_requirement_document_prd.md), UC-03 และ BR-TOPUP-01
> AC3.4–AC3.8 เป็นข้อเสนอเพิ่มเติม; ยังไม่ได้เพิ่มลง PRD

## ผู้ใช้งาน

ผู้ปกครองที่ยืนยันตัวตนและมีสิทธิ์ดูแลนักเรียน ผ่าน Parent Mobile App

## เงื่อนไขก่อนเริ่ม

- นักเรียนและ Wallet มีอยู่ในระบบ
- ผู้ปกครองมีสิทธิ์เติมเงินให้ Wallet ของนักเรียนคนนั้น
- ระบบมี policy ยอดเติมเงินขั้นต่ำและสูงสุดที่ Staff ตั้งไว้
- Parent ระบุยอดเติมเงินและชำระผ่าน Payment Gateway

## ขั้นตอนหลัก

1. Parent เลือกนักเรียนและระบุยอดเติมเงิน
2. ระบบตรวจสอบตัวตน, สิทธิ์ดูแลนักเรียน และยอดตาม policy ขั้นต่ำ/สูงสุด
3. ระบบเริ่มรายการชำระผ่าน Gateway
4. เมื่อ Gateway ยืนยันการชำระสำเร็จ ระบบเพิ่มยอด Wallet เพียงครั้งเดียว
5. หากยอด Wallet ติดลบจากรายการ Offline ระบบนำยอดเติมไปหักกลบยอดติดลบตามลำดับ
6. ระบบส่งผลรายการเติมเงินกลับให้ Parent

## กฎทางธุรกิจ

- ขั้นต่ำและขั้นสูงเป็นค่าที่กำหนดจาก system settings โดย Staff (BR-TOPUP-01); ตัวอย่างใน AC คือขั้นต่ำ 50 บาทและสูงสุด 2,000 บาท
- การปฏิเสธยอดที่ไม่ผ่าน policy ต้องไม่เปลี่ยนยอด Wallet
- การเติมเงิน 100 บาทเมื่อ Wallet เป็น -30 บาท ทำให้ยอดสุทธิเป็น 70 บาท (AC3.3)
- ข้อเสนอ: เพิ่มยอด Wallet หลังยืนยันชำระสำเร็จเท่านั้น และ Gateway callback/retry ต้องไม่ทำให้เติมยอดซ้ำ
- ขอบเขตว่า minimum/maximum รวมค่าขอบหรือไม่ และวิธีจัดการผล Gateway ที่ timeout ยังต้องรีวิว

## Acceptance criteria

| รหัส AC | Given | When | Then |
|---|---|---|---|
| **AC3.1** | Staff ตั้งขั้นต่ำ 50 บาทและสูงสุด 2,000 บาท | Parent เติม 100 บาทและ Gateway ยืนยันชำระสำเร็จ | สำเร็จ (`200 OK`): ยอดเติมเข้า Wallet |
| **AC3.2** | Staff ตั้งขั้นต่ำ 50 บาท | Parent ขอเติม 30 บาท | ปฏิเสธ (`400 INVALID_TOPUP_AMOUNT`); แจ้งขั้นต่ำ 50 บาทและไม่เปลี่ยน Wallet |
| **AC3.3** | Wallet มียอด `-30.00` บาทจาก Offline conflict | Parent เติม `100.00` บาทสำเร็จ | สำเร็จ (`200 OK`): หักกลบยอดติดลบและยอด Wallet เป็น `70.00` บาท |
| **AC3.4** *(เสนอ)* | Staff ตั้งยอดสูงสุด 2,000 บาท | Parent ขอเติม `2,001` บาท | ปฏิเสธ (`400 INVALID_TOPUP_AMOUNT`); ไม่เปลี่ยน Wallet |
| **AC3.5** *(เสนอ)* | Student ID ที่ระบุไม่มีในระบบ | Parent ส่งคำขอเติมเงิน | ปฏิเสธ (`404 STUDENT_NOT_FOUND`); ไม่สร้างรายการเติมเงินหรือเปลี่ยน Wallet |
| **AC3.6** *(เสนอ)* | ผู้เรียกไม่ได้ login หรือไม่ได้รับอนุญาตให้ดูแลนักเรียน | ผู้เรียกส่งคำขอเติมเงินให้ Student ID นั้น | ปฏิเสธ (`401 AUTHENTICATION_REQUIRED` หรือ `403 PARENT_STUDENT_ACCESS_DENIED`); ไม่เปลี่ยน Wallet |
| **AC3.7** *(เสนอ)* | Payment Gateway ปฏิเสธหรือล้มเหลวในการชำระ | Parent พยายามเติมเงิน | ปฏิเสธ (`502 PAYMENT_GATEWAY_FAILED`); ยอด Wallet ไม่เพิ่ม |
| **AC3.8** *(เสนอ)* | Gateway เคยยืนยันรายการเติมเงินนี้และ Wallet ได้รับยอดแล้ว | Gateway ส่ง callback เดิมซ้ำ | คืนผลรายการเดิม (`200 OK`); ยอด Wallet เพิ่มเพียงครั้งเดียว |

## นอกขอบเขต

- การตั้งค่า/แก้ไขยอดเติมเงินขั้นต่ำและสูงสุดโดย Staff เป็นความสามารถจัดการ system settings ซึ่ง PRD ยังไม่มี use case แยก
- การคืนเงินให้ผู้ปกครองเมื่อ Gateway รับเงินแล้วแต่ระบบไม่สามารถเติม Wallet ได้
- การชำระสินค้าให้ร้านค้าและการ Sync รายการ Offline อยู่ใน UC-05
- Login, reset password และการผูก Parent-Student เป็นข้อกำหนด identity แยกต่างหาก

## คำถามที่ต้องตอบ

- ยอดที่เท่ากับขั้นต่ำหรือสูงสุดให้เติมได้หรือไม่? ข้อเสนอเบื้องต้นคือ inclusive
- เมื่อ Gateway timeout และยังไม่ทราบว่ารับเงินหรือไม่ ให้ค้างสถานะ `pending` แล้วตรวจสอบซ้ำด้วย payment reference หรือให้แจ้งล้มเหลว?
- Gateway/provider ใดเป็นผู้ให้บริการ และใช้ reference/idempotency key แบบใด?
- Gateway ปฏิเสธการชำระ (decline) กับ Gateway ขัดข้อง/timeout ควรตอบ status code เดียวกันหรือไม่?
- หาก Gateway รับเงินแล้วแต่การบันทึกยอด Wallet ล้มเหลว จะ retry/reconcile อย่างไร?
- เมื่อผู้ปกครองไม่ได้ผูกกับนักเรียน ควรตอบ `403` หรือซ่อนการมีอยู่ของนักเรียนด้วย `404`?

## API ที่เกี่ยวข้อง

- `POST /parent/wallet/topup` ตาม traceability matrix ใน PRD
- Error code ของ AC3.4–AC3.7 และ idempotent response ของ AC3.8 เป็นข้อเสนอ; ต้องรีวิวและระบุใน `openapi.yaml` ก่อน implementation
